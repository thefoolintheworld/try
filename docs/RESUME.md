## 版本 A：详细版（适合作为「项目经历」主体，5-7 行）

**荧烛微光 —— 文学化个人记录与报告生成器（微信小程序）**　|　独立开发　|　TypeScript / LESS / Canvas 2D

个人独立开发的微信小程序，帮助用户把阅读与日常经历转化为文学化叙事报告并分享。覆盖成就记录、报告生成、年度回顾、读者人格分析、习惯打卡等模块，27 个页面、32 个工具模块。

- 设计并实现自研**模板引擎**（变量插值 / 条件块 / 循环块），驱动报告自动生成与 PPT 化样式编辑器
- 构建 **WXSS 预览 ↔ Canvas 导出双渲染同源架构**，用归一化坐标（0~1 小数）解决预览 1:1 与导出 3:4 比例不一致问题，实现所见即所得
- 搭建 **3 条构建期 lint**，每条都源自一次真实线上 bug（LESS 颜色函数真机白屏 / 聚合器误读脏数据 / 事件绑定静默失效），将事故预防前置到构建期
- 维护 **12 套测试、565 条断言**的回归网，支撑 7 个版本迭代零数据丢失、零回归
- 实现 Canvas **长图拼接、超长卡自动拆分、dpr 高清适配**，海报在任意机型不模糊

## 面试讲解话术（按面试官常见提问组织）

### 「这个项目最难的点是什么？」

> 最难的是报告编辑器的双渲染一致性。用户在编辑器预览里把一段文字旋转 15 度、拖到卡片某个位置，导出海报时必须一模一样。但预览走 WXSS（浏览器渲染，1:1 比例），导出走 Canvas 2D（手工绘制，3:4 比例）——两套引擎、比例还不一样。
>
> 我用归一化坐标解决了比例问题：几何位置不存 rpx 或 px，而是存 0~1 的小数（相对正文区）。两边各自乘以自己的尺寸，预览里 50% 是中间，导出里 50% 也是中间，所见即所得自动成立。

### 「你遇到什么技术坑？怎么解决的？」

> 旋转中心。最初 Canvas 绕文字左边缘旋转，WXSS 默认绕元素中心转。左对齐文字旋转后两边明显不一致——预览微微倾斜，导出甩到一边。
>
> 修复方法：Canvas 先用 `measureText` 量出这一行的实际像素宽，按对齐方式算出真正的水平中心，再围绕它旋转。这样 Canvas 的旋转中心和 CSS 的 `transform-origin: 50% 50%` 语义对齐了。
>
> 为了防止以后再加视觉效果又漏改一边，我把流式段和自由定位段的绘制逻辑抽成公共函数，并加了 60 多条测试断言锁住关键不变量。

### 「为什么不用现成的方案？」

> 试过。小程序生态里要么是富文本组件（导出海报不行），要么是 canvas 海报库（编辑预览不行），没有一套同时解决「编辑预览 + 海报导出」且样式一致的方案。自己写这套 dual-render 架构，反而比硬凑两个不兼容的库更可控。

### 「合规边界是怎么影响技术选型的？」

> 微信个人主体小程序有很多限制：不能云开发（涉及登录和数据上传）、不能调 AI（触发「深度合成」类目）、不能抓豆瓣。这些约束反过来逼出了项目最有特色的部分——报告文案不靠 AI 生成，而是靠自研模板引擎拼装；数据不存云端，而是做了完整的本地存储 + 迁移 + 备份机制。约束本身成了设计驱动力。

### 「测试和工程化怎么做的？」

> 三条构建期 lint，每条都对应一个真实踩过的坑。比如 LESS 编译期颜色函数（`fade()`/`lighten()`）在真机上会让页面白屏——因为项目的颜色变量是 CSS 变量别名，LESS 编译期拿到 `var(--x)` 解析不出颜色就报错。我加了条 lint 扫所有 .less 文件禁用这些函数，从根上防住。
>
> 测试是 12 套、565 条断言，纯 Node 跑、零依赖，覆盖模板引擎、canvas 拆卡、人格算法、备份恢复这些核心路径。每次改动几秒钟就能验证有没有回归。
